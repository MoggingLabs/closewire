## Security: client OAuth credentials, and why the first fix was wrong

`GET /agency/source` returns each source's **`accessToken`** and **`key`** — the
GoHighLevel OAuth credentials for a *client's* sub-account. These are not the Closebot API
key, so `Config.scrub()` does not mask them, and nothing in phases 01–04 would have caught
them leaking into a log, an error, or a model context.

**The first fix was per-module and it was wrong.** `sources.*` redacted; `bots.*` did not
— and a bot row embeds `sources: [{id, name, key, …}]` carrying the *identical* credential,
confirmed byte-identical by SHA-256 fingerprint for three client sub-accounts across two
bots. Two critics found it independently. Patching `bots.py` would have left every future
module — writes, runtime, MCP tools — free to leak the same field again, because
protection was a thing each author had to remember.

Note also that the embedded copy identifies itself with **`id`**, not `sourceId`, so any
rule that tried to recognise "this payload looks like a source" would have missed it.

**Redaction is now default-deny at the transport boundary** — `RestClient._handle`, the
same choke point pacing uses. Every response, from any endpoint, generated or hand-written,
present or added later, is scrubbed unless the caller explicitly opts out. A new endpoint
is safe without its author doing anything. Implementation and rationale live in
`closewire_client/redaction.py`; **no redaction logic remains in `endpoints/`**.

### Round 2: the boundary was real but not complete

Two critics blocked again, and both were right about the same class of thing — a guarantee
stated but not enforced everywhere.

**The error branch bypassed the scrubber.** `_handle` raised `ClosebotAPIError` before
reaching `_scrub_credentials`, so every non-2xx body skipped the boundary — inside the very
method documented as covering "every response", in the branch that runs first. `cli/main.py`
prints those bodies and `errors.py` embeds them in the exception message. Fixed by
restructuring: **decode once, scrub once, then branch on status**, so no exit from
`_handle` can skip it. Live errors happen to return RFC-7807 problem+json with no resource
echo, so this was structural rather than an active leak — but it was still false.

**The path-based exemption was bypassable.** `is_schema_path` matched by *substring*
against an un-normalized path, so `/agency/source?q=/bot/nodeDescriptors` returned raw
credentials, and `/bot/nodeDescriptors/../../agency/source` fetched the real source list
(httpx normalizes the wire path) while the exemption had already been granted on the
pre-normalization string. One crafted path both fetched sources and disabled the control,
reachable anywhere an id is interpolated — which is where phase 11 will put model-supplied
input.

Pattern-matching a caller-influenceable string is not a control. **Path matching is gone.**
The catalogue now opts out explicitly at its single call site via `static_schema=True`.

### The escape hatches now

| Hatch | Purpose | Guard |
| :-- | :-- | :-- |
| `include_secrets=True` | Phase 10 must read a real OAuth token | **Capability, not an argument**: requires `RestClient(allow_secrets=True)`, else `PermissionError`. A tool on an ordinary client has no path to a credential however its arguments are shaped. Logs at WARNING. |
| `static_schema=True` | The node catalogue uses `key` for property names (`EnableGhlBooking`, `UseAI`); scrubbing corrupts what phase 07 validates against | **Mechanically the same bypass** as `include_secrets`, and *not* capability-gated — it is honest to call it a second hole. What limits it is unreachability, verified by a critic across all 130 call sites in 25 modules: **no wrapper forwards `**kwargs` into `request`**, so setting it requires editing source. One call site, `bots.node_descriptors`. Its safety was verified live across all 5 flow versions on all 3 bots (125 nodes): **zero** credential-named fields in flow graphs; the catalogue's 17 are all property names. |

Two more holes closed at the same time, both from the same "stated but not enforced" family:

- **Text bodies bypassed redaction entirely** — `redact_secrets` cannot walk a bare string,
  and some endpoints return JSON with a non-JSON content type. Now parsed, scrubbed, and
  re-serialized.
- **`<redacted>` round-tripped into write bodies.** Read-modify-write is phase 07's natural
  shape, and sending a masked read back would have overwritten a live client's OAuth key
  with the literal string. Writes now **refuse** a body containing the sentinel.

`tests/test_redaction.py` pins all of it, including the three demonstrated bypasses as
explicit regressions (see the verification block below for the current count). Verified offline: an endpoint with **no wrapper at all**,
returning a credential under an invented field name, comes back masked — and so does a 400
carrying one.

### Corrections to this document, found by review

1. **`get_ai_toggle` was miscredited.** The table originally attributed
   `mostRecentFailureReason: 'ai_off'` to `get_ai_toggle`. That field comes from
   `leads.get`; `get_ai_toggle` returns `{enabled, applicable, reason}` with `reason:
   None`. The ✅ on `enabled: False` ↔ toggle-off still holds, but a later phase reading
   `get_ai_toggle().reason` to explain the banner would always get nothing. Split into two
   rows above.
2. **`booking_graph` was recorded as "0 points, all resolutions" and ✅-matched to the
   dashboard's "Booking Rate 0.0%".** That evidence was vacuous: the account has **44
   bookings across 8 months**, and the zero was an artifact of a hard-coded 30-day window
   that genuinely contains none. The verification now sweeps 730 days and gets 42/42/8
   points totalling 44 bookings, and **fails the run** if the monthly series is empty.
   `booking_graph` also now rejects an inverted `start`/`end` locally, since an inverted
   range returns `[]` — indistinguishable from "no bookings", the exact shape of this
   mistake.
3. **"32 public functions" was wrong** — there are 34, and nine of them were never called.
   The script now asserts coverage instead of claiming it.
4. **Two rows carry no screenshot**: `sources.list_channels` and the `sourceId` URL check.
   Both were observed in the browser — the channels list from the source detail nav, the id
   from the address the navigation tool reported — but neither is in a captured image.
   Marked here rather than left to look better-evidenced than they are.

### Discrepancies found by the cross-check

1. **Timestamps are naive and rendered local.** API `lastMessageTime: 2026-07-22T00:49:17`
   displays as "Jul 22 at 01:49 AM" — a one-hour offset, no timezone in the payload.
   Anything that compares or filters on time across phases must account for this.
2. **`summary.currentMonthMessageCount` (5) vs the dashboard's "Responses 4/500".** Close
   but not equal: the summary counts messages, the usage panel counts billable *responses*.
   Different denominators, not a bug — but do not treat them as the same number.
3. **`bots.get_steps` was not opened in the Job Flow builder.** The API returns 34 nodes and
   `describe_flow` resolves every one against the catalogue, but I did not open the builder
   and count nodes by eye. This is the one row above that is **API-verified only**, and it
   is the deliverable phase 07 depends on most. Flagged rather than claimed.
4. **Calendars, fields, and tags have no source-level UI surface.** The API returns 3
   calendars, 126 fields across `contact`/`customValue`/`location`, and 71 tags for
   the probed source, but the source detail page exposes Setup / Settings / User
   Access / Variables / Availability / Channels only — these lists appear when configuring
   a Booking or ModifyTags node inside a flow. Recorded as **no direct UI surface**, not as
   a pass. Phase 07 will be able to corroborate them from the node editor.

### What the verification script now does that it did not

Round 1 blocked on evidence, so the script was rebuilt around three properties it lacked:

- **Complete** — it calls every public API function and asserts coverage against
  `__all__`, so a function added later without a probe fails the run. It previously missed
  nine, two of which were broken.
- **Fails on anything new** — non-zero on any unexpected failure, while the two known
  server-side timeouts are listed separately so the exit code keeps its signal. A leak or
  a coverage gap can never be downgraded, whatever its label. It previously returned 0
  unconditionally; a run printing `UNREDACTED SECRETS` still exited 0.
- **Detects leaks past row 0** — the secret check walks the whole structure. It previously
  used `blob.find()`, so a masked first row hid an unmasked second one — which is exactly
  why it reported a clean sweep over a real leak.

It also exercises `get_steps` for **every bot × every version** (5 graphs), not just the
first bot's newest version — which had hidden that `latest_version` returns an unpublished
draft.
